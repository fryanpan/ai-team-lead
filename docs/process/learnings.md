## `grep -r` Silently Skips The Private Files, Because Every One Of Them Is A Symlink (2026-08-17)

- **`grep -rl "weekly.review" --include="*.yaml" .` returns nothing in this repo; `grep -l "weekly-review" registry.yaml` returns a hit.** `grep -r` does not follow symlinks encountered during recursion — only `-R` does. And per the "Private Files" section of `CLAUDE.md`, *every* gitignored private file here is a symlink from the main worktree: `registry.yaml`, `docs/process/retrospective.md`, `docs/process/propagation-log.md`. So the highest-value files in the repo are exactly the ones a recursive grep cannot see.
- **The failure is a silent empty result, which reads as a confident "it does not exist."** I searched for a "Weekly Review" agent, got zero hits, cross-checked against `list_peers` (it wasn't running — the fleet is lean by design, so absence there means nothing either), and told Bryan on a review thread that no such project existed. It is registry entry `weekly-review`, with a repo, a Linear team, and `respawn: true`. Two independent checks, both structurally blind to the answer, agreeing on the wrong one.
- **Use `grep -R`, or name the file directly.** `-R` follows symlinks; `Grep`/`rg` follow them only with `--follow`. When the question is "does the fleet have X," read `registry.yaml` by name — it is the authority, and it is precisely the file recursion drops.
- **`list_peers` is not a registry.** It enumerates *running* sessions. In a deliberately lean fleet most registered projects are idle at any moment, so "not in `list_peers`" is not evidence of "not a project." Don't stack it with a grep and call that corroboration.
- **Same family as the leak-gate entry below**: a check whose sources silently failed to resolve, reporting clean. The generalizable half — **before concluding something is absent, confirm your search could have found it if it were present.** Here that was one command: grep the file by name.

## Every Step Ran And Nobody Owned The Outcome — The Undischarged-Obligation Shape (2026-08-17)

- **Four failures this week, four different systems, one shape: each mechanism did exactly what it was defined to do, no step was broken, and the thing the pipeline existed to accomplish was nobody's job.** The tell is that every check is green *and* correct — there is no failing component to find, which is why these survive review and outlast several people looking straight at them.
- **The four, so the pattern is falsifiable rather than a slogan:**
  - **Leak gate.** Both layers ran, one had no patterns and one had no key. Each exited 0 truthfully. No step was defined as "assert the sources resolved."
  - **Drift strip.** `behind: []` rendered "nobody is behind" while nine sessions were. Its domain is *sessions that attached to the board* — it measured participation faithfully. Nothing was defined as measuring the fleet.
  - **`/mcp reconnect`.** Returned "Reconnected 0 of 4" — an honest decline. Nothing was defined as delivering the new bundle, so the honest decline and a successful delivery were equally acceptable outcomes.
  - **Capture → triage.** A pasted paragraph became two raw rows, one titled with a clipped fragment. Capture is deliberately dumb so an idea is never lost; triage is defined as *placement only*. Nothing is defined as rewriting a row into something pickup-able, so the fragment title is permanent and every check is green.
- **The diagnostic question that finds these, and it is not "what broke":** *which step is defined as discharging this obligation?* If the answer is "the pipeline as a whole," there is no owner and the obligation is undischarged. Ask it of the outcome you actually want, not of the steps you have — the steps will all defend themselves.
- **Why they are invisible to the usual instincts.** Green means "every defined step succeeded," and that is true. Adding a check to an existing step cannot help, because no existing step is wrong. The fix is always to *define a step that owns the outcome*, which reads like scope creep at review time and is the entire repair.
- **Distinguish from the "verify the artifact" family below.** Those are cases where a step LIED — a success message that described an operation nobody wanted (`✔ Successfully updated marketplace` copying nothing). Here nothing lies. Same green, opposite cause: there, a step over-claimed; here, no step claimed at all. Fixing one with the other's remedy fails — auditing outputs harder will never surface a missing owner.

## SessionStart RULES Inject From The WORKING TREE — So A Directory-Source Plugin Needs No Bump And No Update (2026-08-17)

- **This closes the gap the 2026-08-11 entry explicitly left open** ("whether skills/rules also load from the working tree rather than the cache was NOT tested"). For a **directory-source** marketplace, the rules concatenated by `hooks/session-start.sh` come from the working tree. Measured, not inferred.
- **The measurement, because the timeline is the whole proof.** `effort-estimates.md` was committed to the working tree at 2026-08-13 03:49. The `0.5.0` cache dir that first contains that file was born at **18:02** the same day. The rule appears in this session's injected context from the **05:51** injection onward — four separate injections (05:51, 09:36, 13:48, 14:40) carried a rule that existed **only** in the working tree, twelve hours before any cache held it. The 03:46 injection, three minutes before the commit, has zero hits.
- **Consequence, and it is the useful half: a fleet rules change is delivered by a RESTART ALONE.** No version bump in either manifest, no `claude plugin update`, no marketplace refresh. The four-step deploy documented below applies to a **GitHub-source** plugin; for `team-lead-fleet` it is three steps too many, and the bump that "made the previous rollout land" was almost certainly incidental.
- **Do NOT extend this to skills.** Proven for rules reaching context via the SessionStart hook. Skills are discovered by a different mechanism, and nothing here tests them. A plugin can therefore deliver its *rules* from the working tree and its *skills* from the cache, which is a genuinely confusing shape — check before assuming either.
- **`installPath` in `installed_plugins.json` is not the answer to this question.** It records the version-keyed cache dir for a directory-source plugin too (`.../team-lead-fleet/0.5.0`), which reads exactly like "the cache is what runs" and is what sent me looking the wrong way for ten minutes. The record's path and the hook's read path are different things.
- **Two cache dirs can both lack `.orphaned_at` at once** — `0.4.0` and `0.5.0` are both unmarked here. Any "pick the current version" logic keyed only on the absence of that marker has more than one answer; take the highest semver among unmarked dirs.
- **Practical split for delivering a fleet-wide behavior change:** put it in `team-lead-fleet/rules/` and it reaches every peer at its next restart, today. Put it in a GitHub-source plugin's skill and it reaches nobody until each peer runs the update and restarts. Same words, two delivery latencies, and the difference is which repo you typed them into.

## A Restart Can Move A Session BACKWARDS Onto An Older Plugin — Marketplace Source Decides, Not The Repo Shape (2026-08-13)

- **This bounds the "MCP servers run from the WORKING TREE" entry below, which is true only for a DIRECTORY-source marketplace.** `claude plugin marketplace list` is the discriminator, and it disagrees with intuition: a plugin whose code you have checked out at `~/dev/<repo>` can still be registered as a **GitHub** source, in which case `${CLAUDE_PLUGIN_ROOT}` resolves to the version-keyed cache and the working tree is irrelevant. Two plugins in this fleet, both with local checkouts, resolve opposite ways.
- **The consequence is the non-obvious one: restarting a session to "pick up the latest" can DOWNGRADE it.** A peer whose previous incarnation happened to be running an MCP server out of its own working tree (0.1.15) came back on the cache (0.1.12) after a respawn. Restart does not fetch; it loads whatever the cache holds at that instant. **`claude plugin update` is the delivery step, and the restart only ratifies it** — in that order, or the restart is worse than doing nothing.
- **A version number is not evidence; grep the bundle for the symbol you need.** `set_task_dependencies` appeared 2x in the 0.1.15 bundle and **0x** in 0.1.12, which is what proved the downgrade. Two other tools the peer had also named as missing (`next_tasks`, `get_workspace`) were present in *both* — so a probe keyed on either of those would have reported everything fine while the actually-blocking tool was absent. **Pick the discriminating symbol, not a representative one.**
- **Fixing this mid-fleet-restart splits the fleet across two versions, silently.** Eight peers restarted before the update ran and stayed on 0.1.12; one restarted after and got 0.1.15. Nothing anywhere reports the split — each peer looks correct from inside. If a change must reach everyone, the update has to precede the *first* kill, not follow the last spawn.
- **Same family as the fourth-instance partial-refresh entries below** (`/login` moves billing only; reconnect moves schemas not env; `--continue` moves the transcript not the injected rules). Add this one: **a respawn moves the process, not the bytes it loads.**

## Both Layers Of The Leak Gate Had Been Inert For Weeks, And Every Signal Said PASS (2026-08-13)

- **Two copies of `scrub-check.py` had opposite halves dead, and neither warned.** One had a `FLEET_REGISTRY` pointing at a pre-rename path, so zero project names compiled; the other had a `DENYLIST_PATH` pointing at a directory the file had never been moved into, so zero denylist patterns compiled. Each survived because the *other* half kept the pattern list non-empty, and the guard was written to catch "no patterns at all" rather than **"a source I expected is missing."** That distinction is the whole finding: a half-configured scanner reports a clean push it never performed.
- **Layer 2 was not merely half-dead, it was entirely off.** `scrub-haiku.py` read its key from `SCRUB_HAIKU_API_KEY` / `ANTHROPIC_API_KEY` only; the key lives in the Keychain precisely *because* every session on this machine runs as the same user and inherits the same env. So it printed "no API key — skipping" and exited **0** on every push for weeks. **An exit 0 from a component that declined to run is indistinguishable from an exit 0 from a component that ran and found nothing** — unless you make declining an error.
- **`scrub-check.py` ignores stdin entirely.** A prior "clean scan" was produced by piping a diff into it: it scanned nothing and exited 0. A scanner given no file arguments must exit non-zero, not succeed vacuously.
- **A positive control proves nothing if it runs against the wrong data.** The port's self-test planted a name in a temp fixture and pointed `SCRUB_REGISTRY` at it — but `find_registry()` returned the repo-local `registry.yaml` *before* consulting the override, so the test scanned the real registry, didn't find the planted name, and passed. It passed in the repo with no root `registry.yaml` and failed in the one that has it. **"Authoritative except in repos that carry their own registry" is authoritative nowhere that counts.**
- **The escape hatch for a stranger's clone was dead code, and only a seam could have caught it.** `resolved = sum(1 for s in (registry, DENYLIST_PATH) if s)` was never 0 because `find_registry()` had stopped returning `None` — so every push from a clean clone of the public repo would have exited 2, telling a stranger to fix config paths that were never theirs. The two guards disagreed about whether "not found" is spelled `None` or a path-that-doesn't-exist. **The branch was unreachable from the environment in either repo shape**, so no amount of "re-run it in the other checkout" would have found it; extracting a pure `decide_sources(...)` and tabling all eight combinations is what did. **A branch reachable only in the field is untested by construction.**
- **The one file guaranteed never to be scanned is the file most likely to contain an example project name.** `scrub-check.py` is in its own `SKIP_PATHS` — it has to be, since it quotes denylist keywords as examples. A real private name sat in a code comment in a *public* repo for exactly that reason. Scanning ours found 0 project names but 2 self-matches in the Haiku prompt's own category list ("Form 8606…", "HbA1c…"), which is why the skip exists and why removing it isn't the fix. Closing this properly needs an allowlist of known self-referential lines so a *new* match still surfaces.
- **A commit that deletes a leak was blocked as a leak** — the Haiku layer read the `-` lines of a removal diff as content going public. Judge added lines only. This is the purest form of the false positive that trains people into `SCRUB_SKIP=1`, which is the failure the whole gate exists to avoid.
- **Registry semantics: `public: true` and `mentionable: true` are two keys on purpose.** The gate asks "is this name safe to say"; the flip-public flow asks "is this repo public today." Collapsing them forces the registry to assert a private repo is public, and the next reader inherits the falsehood. Verified all three newly-cleared repos were still PRIVATE on GitHub before writing the field — the "simple path" would have written a lie into the one file that is supposed to be authoritative about visibility.
- **General shape, fourth sighting this month:** a path constant moved, nothing asserted the source resolved, and every external signal (exit 0, "no patterns configured" silence, a green self-test) reported success. Same family as `✔ Successfully updated marketplace` copying nothing and as trusting the process table for MCP health. **Verify the artifact, and prove the check can still see — a green is only evidence if you have watched a red.**

## `$HOME` Is Not The Boot Disk — Four Dotfile Dirs Are Symlinks Onto The Secondary Volume (2026-08-11)

- **`~/.claude`, `~/.config`, `~/.local` and `~/.bun` are each a symlink into `/Volumes/Data`.** So "put it under `$HOME` and launchd can read it" is false, and it is false in the most misleading way possible: `~/Library` *is* real boot disk (`disk3s5`), so half the home directory works and half doesn't, with nothing in the path to tell them apart. `df -h <path>` is the check; a path's shape tells you nothing.
- **This is what broke the plugin-staleness check, and the earlier entries pointed the wrong way.** The prior finding was written as "launchd cannot exec a *script* on the secondary volume." It is broader: an Apple-signed binary under launchd is denied **every** operation there — exec, read, and even `os.listdir`/`stat`. Delegating just the manifest *read* to bun left the cache *scan* in python, and `~/.claude/plugins/cache` is the Data volume, so all five checks raised `PermissionError`. `/usr/bin/test -e` is no escape either — it is Apple-signed too.
- **The generalizable fix is a deploy root that is provably boot disk, and `/opt` is the only obvious one.** It needs one `sudo mkdir` + `chown` because it is root-owned, and in exchange it can't be silently repointed by a dotfile symlink later. `~/Library/Application Support/<app>/` works as a fallback but is a strange home for executables.
- **`bun -e` argv has no script slot: it is `[bunPath, ...args]`, so arguments start at `argv[1]`, not `argv[2]`.** Written as `slice(2)` out of node habit, the first argument was silently dropped and the probe read a garbage path — which surfaced as the *same* "cannot read plugin cache" message as the real permission bug. Two different faults with one error string is how a fix gets called a non-fix; make the failure paths say different things.
- **A check that can only ever return one answer is not a check.** The token-presence check was `os.path.exists` on a `~/.config` path, so under launchd it would have reported MISSING forever — including after the file was created. Caught only by testing the probe in *both* directions against a file that exists and one that doesn't. Same family as the permanently-red scrub flag: verify a green is reachable, not just that a red fires.

## A Health Check Must Assert END STATE — And `pgrep -f` Silently Cannot See The Team-Lead (2026-08-11)

- **Every outage found this week was "running but not working," so a liveness check would have called all of them green.** The github broker was up on its port with no token and never polled; the email watcher had been alive 2.5 days emitting nothing but 403s; the notion receiver was bound to a port its tunnel didn't route to; two servers held one port in different address families. **The design rule that falls out: assert the observable end state — one listener on the port, the endpoint returns the expected marker, the error stream is quiet, the launch line carries the flag — never a PID.**
- **A `/health` endpoint returning 200 is not health, and this one proves it.** The github broker answers `{"ok":true,"sessions":0}` while having no token and doing nothing at all. The only evidence that distinguishes working from inert is the presence of `~/.config/github-claude-channel/env`. **If a daemon can be inert and still answer its own health endpoint, the health endpoint is not the check.**
- **`pgrep -f` omitted the team-lead's own process, and nothing reported it.** `pgrep -U <uid> -f 'bin/claude'` returned nine sessions and silently skipped PID 1910, whose `ps` command line is a plain match (`/Users/bryanchan/.local/bin/claude …`, 237 chars — not a truncation case). The first version of the checker therefore reported "NO SESSION at ai-team-lead" *from inside the ai-team-lead session*. **Enumerate from `ps -axww -o pid=,uid=,command=` and filter yourself.** A monitor that cannot see the team-lead is worse than none, and this failure is invisible — same family as trusting the process table for MCP health.
- **`osascript display notification` breaks if you interpolate the message into the script source.** The very first RED it fired on contained JSON with escaped quotes (`\"CONSUMER_INVALID\"`) and the AppleScript parse died with `-2741`. Escaping quotes is not enough — backslashes break it too. **Pass the text as argv** (`-e 'on run argv' -e 'display notification (item 1 of argv) …' -e 'end run' MSG TITLE`). Caught only because `notify()` was made to report its own failure; with `capture_output` and no check it would have run "successfully" forever while no alert ever reached anyone.
- **`respawn: true` does not mean "must be running."** Generating session checks from it made the first run report five deliberately-idle projects as failures — the fleet is lean by design. Added an explicit `always_up: true` registry field (team-lead + the always-up assistant). **A monitor that reports intended state as failure is how you train yourself to ignore it**, which is the exact problem this was built to solve.
- **The monitor itself had to be immune to the bug it monitors.** Under launchd an Apple-signed interpreter cannot open *any* file on `/Volumes/Data` (`[Errno 1] Operation not permitted`), so the source lives in the repo but `install_healthcheck.py` deploys a copy plus a generated config to `~/Library/Application Support/team-lead/`. Every path it reads at runtime is boot-disk; `ps`/`lsof`/`launchctl`/`curl` are fine because they read kernel state or the network.
- **Zero tokens on green is what makes it sustainable.** A plain script runs 3×/day under launchd, prints RED lines to a log, writes a status JSON, and fires a notification only on RED. No model runs unless something is actually broken.
- **Verify a monitor by breaking something.** Booting the broker out flipped exactly three checks red (launchd label, port, HTTP) and restoring it returned them to green — that end-to-end proof is the difference between a check that runs and a check that detects.

## A Daemon Spawned By An MCP Server Is Session-Scoped — launchd Is The Fix, And It Cannot Exec Off The Secondary Volume (2026-08-11)

- **Both channel bridges started their own background daemon from inside the MCP server** — notion's `ensureReceiver()` and github's `ensureBroker()`, each spawned detached by whichever Claude Code session loaded the plugin first. That survives the spawning session dying, but **nothing brings it back after a reboot** until some session happens to start; until then Notion webhooks hit a tunnel with no listener and are dropped. Same durability class as the session-scoped `CronCreate` jobs.
- **launchd ownership is compatible precisely because both `ensureX()` functions health-check before spawning.** They log "already running" and return, so a launchd-owned daemon is adopted rather than duplicated. Check for that guard before putting one of these under launchd — without it you get two daemons racing for the port.
- **Verify KeepAlive by killing the thing, not by reading the plist.** `KeepAlive={Crashed:true, SuccessfulExit:false}` + `RunAtLoad` was confirmed by `kill -9` and watching launchd return a new PID on a working health endpoint. `launchctl list` showing a PID only proves it started once.
- **A newly-created LaunchAgent installs and runs fine — there is no approval gate on new agents here.** Both bootstrapped and ran first try. This also falsifies the BTM hypothesis in the 2026-07-22 entry for the exit-126 jobs: scheduled agents are still firing on time (one has log entries from its 09:00 slot today), they just die at exec. **Exit 126 with a script on the secondary volume is this bug, not BTM** — the two were merged for three weeks and sent the diagnosis toward a GUI re-approval that would have fixed nothing.
- **But launchd could not exec a shell script living on the secondary volume.** `/Users/bryanchan` is on the boot disk (`disk3s5`); `/Volumes/Data` is a separate SSD. An agent whose `ProgramArguments[0]` is a `.sh` under `/Volumes/Data` dies with `bash: <path>: Operation not permitted` plus `shell-init: getcwd: Operation not permitted` — **exit 126, which reads exactly like the BTM failure and is not it.** The two agents that work exec a boot-disk binary (`~/.bun/bin/bun`) and merely *read* their sources from `/Volumes/Data`, which is permitted.
- **Ruled out by measurement, not inference:** the `~/dev` symlink path (repointing to the real path changed nothing), directory permissions (identical), ACLs (none), `com.apple.quarantine` (absent), and `com.apple.provenance` (present on the *working* file too). Interposing `/bin/bash <script>` did not help either — Apple-signed `/bin/bash` is itself gated, while the user-installed bun binary is not. **The distinguishing factor is which binary launchd execs, not which volume the data is on.**
- **Practical rule: put the executable on the boot disk and the data wherever you like.** A wrapper script under `/Volumes/Data` cannot be a LaunchAgent's program on this machine.

## Enabling A Plugin Gives You TOOLS; Only A Launch FLAG Gives You The WAKE (2026-08-11)

- **`enabledPlugins` in `~/.claude/settings.json` had notion-channel, github-claude-channel and sentry-claude-channel all `true` for weeks, and not one session was subscribed to any of them.** The channel half comes from a separate mechanism — a `--channels` / `--dangerously-load-development-channels` flag on the launch line — and Bryan's zsh `claude()` function named only discord, claude-hive, and live-feedback. So the tools were reachable and no inbound event could ever wake anybody. **Two independent halves; having only one looks fine from inside the session and is dead from outside.** Same shape as the direct-Discord-registration bug (tools without the wake) — that entry framed it as a workaround quirk; it is actually the general rule.
- **The zsh function is the single canonical place for these flags, and respawn.py deliberately does NOT duplicate them** — it spawns `zsh -ic "claude --continue"`, so the function applies. Inlining them there too produces doubled argv. `self-respawn.sh` goes through the same path, so the team-lead picks them up as well.
- **Fleet-wide subscription was safe here only because both new channels are opt-in by subscription.** notion routes by `pageId` subscribers, github by a per-session `watchedRepos` set; joining the channel delivers nothing until the session calls `notion_watch_page` / `watch_repo`. Discord is the opposite and needs per-peer `DISCORD_STATE_DIR` scoping or one post fans out to every peer. **Check the routing model before adding a channel fleet-wide** — "opt-in by watch" and "broadcast to all subscribers" look identical from the plugin manifest.

## A Stale `.env` Silently Overrode A Port Fix And Made Two Servers Collide (2026-08-11)

- **The port move to 8791 was in the source, in the comments, and in the cloudflared tunnel config — and the receiver still bound 8787,** because `~/dev/notion-channel-mcp/.env` carried a leftover `NOTION_RECEIVER_PORT=8787` and bun auto-loads `.env` from the process cwd. `process.env.X ?? "8791"` means the stale file always wins. **A fix applied to the default is not applied to anything that overrides the default.**
- **Both halves of the resulting breakage were silent.** The tunnel forwarded `notion-bridge.<domain> → localhost:8791` where nothing listened, so every Notion webhook was dropped; meanwhile the receiver squatted `127.0.0.1:8787` alongside live-feedback's IPv6 `*:8787`. Both bound successfully (different address families, and the more specific IPv4 bind wins those connections), so nothing errored anywhere.
- **It began the same morning the plugin was first un-suppressed** — the dedup fix made a server that had never loaded start loading, and it immediately collided with what had moved in during its absence. The prior entry predicted exactly this and it still took a port-by-port check to find. **After un-suppressing a long-dead server, verify what it BINDS, not just that it connects.**
- **Verification that actually settles it is the end-to-end path, not the process.** `lsof` on both ports plus `curl` against the public tunnel hostname and against both `127.0.0.1` and `localhost` — a process on a port proves nothing about which listener a given client reaches.
- **Ordering trap worth remembering:** `subprocess.Popen(preexec_fn=os.setsid, start_new_session=True)` raises; `start_new_session=True` alone is the macOS-safe detach (there is still no `setsid(1)`).

## For A Directory-Source Plugin, The MCP Server Runs From The WORKING TREE — Not The Cache (2026-08-11)

> **Scope check first — see the 2026-08-13 entry at the top of this file.** This holds only for a marketplace whose source is a **Directory**. A plugin can have a local checkout and still be registered as a **GitHub** source, in which case the cache is what runs and a restart can move a session onto an *older* build. Run `claude plugin marketplace list` before applying anything below.

- **This corrects the deploy model the rest of this file teaches.** Every entry below about `claude plugin update` and the version-keyed cache is written as though the cache is what runs. For a directory-source marketplace's **MCP servers**, it isn't: `${CLAUDE_PLUGIN_ROOT}` resolves to the source dir (`~/dev/<repo>`), so whatever is checked out in that working tree is what the next session spawns. `installed_plugins.json` records the cache path, but for this purpose that is bookkeeping.
- **Evidence, not inference:** the live broker (PID 21802) had cwd `/Volumes/Data/.../dev/github-claude-channel`. Established by the channel-plugins agent, 2026-08-11.
- **Consequence that bit us the same day: an unmerged branch is deployed.** Three channel plugins sat on a `fix-mcp-launcher` branch, and any session restarting would have loaded that unreviewed code — no merge, no `plugin update`, no ceremony. **"Deploy timing is mine" is not true by default for these plugins.** If a change must not go live yet, park the working tree on main; a PR sitting unmerged gates nothing.
- **And parking on main only helps while main lacks the fix.** The moment the PR merges, the tree on main carries it. So anything that must land *before* a change goes live has to be in the same PR, not a follow-up.
- **Scope of this finding, honestly:** proven for MCP server launch. Whether skills/rules also load from the working tree rather than the cache was NOT tested — the drift check below assumes the cache, and that assumption is now unverified rather than known-wrong. Don't quietly extend this entry to cover it.

## The Plugin-MCP Dedup Key Is The Command Shape — Identical Commands Silently Delete Servers (2026-08-11)

- **Three channel plugins each declared `"command": "bun", "args": ["./server.ts"]`, so two of the three had never loaded in any session.** The debug log says it outright: `Suppressing plugin MCP server "plugin:notion-channel-mcp:notion-channel": duplicates earlier plugin server "plugin:github-claude-channel:github-claude-channel"`. Nothing else reports it; from inside a session the servers are simply absent.
- **The key, read out of the 2.1.227 binary:** `stdio:` + `JSON.stringify([command, ...args])` plus a sorted env signature that **excludes** `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`. Placeholder expansion runs *before* the dedup pass, so an absolute `${CLAUDE_PLUGIN_ROOT}/...` path does break the tie. Belt-and-braces: give each plugin's launcher a distinct *filename* too, so the key stays distinct even if expansion ever moves after dedup.
- **One fix closed both this and the PATH bug.** A `#!/bin/sh` launcher committed in the plugin and referenced via `${CLAUDE_PLUGIN_ROOT}` makes the command both runtime-independent and per-plugin unique. `bun` had the identical nvm-shaped problem `node` did — it lives in `~/.bun/bin`, so `env -i PATH=/usr/bin:/bin sh -c 'command -v bun'` finds nothing and any non-interactive launch dies at spawn.
- **A launcher does not cover what the server spawns.** `github-claude-channel/server.ts:59` started its broker with a bare `Bun.spawn(["bun", …])` — the server would have come up clean and then failed to start its own broker. Use `process.execPath`, and have the launcher put the resolved runtime first on PATH so descendants inherit it.
- **The suppression was hiding a second bug, and fixing it unmasked one.** notion's receiver binds 8787 and live-feedback already holds 8787; they bind different address families (IPv6 `*:8787` vs IPv4 `127.0.0.1:8787`) so **both bind successfully** and IPv4 traffic goes to whichever grabbed the specific address. `void ensureReceiver()` at module load means this fires on every session start. Nobody had ever hit it because notion never loaded. **When you un-suppress something that has been dead for months, assume it has untested collisions with whatever moved in while it was gone.**
- **A gitignored `.env` that is the only source of a token is a broken install, not untidiness.** bun auto-loads `.env` from cwd, and that was the sole path for notion's integration token — so a stranger's clean install failed every call. Same bar as the launcher fix: if it depends on your dotfiles or your untracked files, it isn't shipped.

## A Plugin Whose MCP Command Is `node` Only Works When Launched From An Interactive Shell (2026-08-10)

- **The whole diagnosis was one word, and I spent hours theorizing before reading it.** `/mcp` reported `Failed to reconnect … ENOENT`. With nvm present: live-feedback **does not appear in the connection list at all**. One PATH bug plus a failure cache reproduces everything I saw. Two faults were never needed to explain it.

A launcher under it resolves node itself (newest `~/.nvm/versions/node/*/bin/node`, then homebrew, then PATH) and execs the entrypoint, surviving an nvm upgrade that a hardcoded absolute path would not. The portable form is a `#!/bin/sh` launcher **committed in the plugin repo** and referenced as `${CLAUDE_PLUGIN_ROOT}/bin/…`, so it ships with the plugin. **Test any plugin fix by asking what a stranger's clean install does** — if the answer depends on your dotfiles, it isn't the fix.
- **Diagnosis was mine to do; the repair was not.** The plugin has an owning agent, and I wrote the shim, the config, and the launcher special-case myself before handing anything over. Team-lead diagnoses across the fleet and delegates the repair to whoever owns the repo — see `feedback_spawn_sessions_dont_self_implement`.

Same lesson as the Discord workaround — a tidier name silently invalidates a permission grant and reads from outside as "still broken."

Any lookup keyed on `realpath(cwd)` finds nothing and silently degrades; `respawn.py` was dropping the channel flag for every worktree session because of it.

Correlating the env got me to the PATH bug and would have sent me the wrong way on the rest — the debug log is what separated them. **Correlation across sessions narrows the field; only the log names the failure.**

- **CORRECTION (2026-08-11): the two exit-126 agents were NOT BTM, and the "launchd never execs" framing is wrong for them.** Their real cause is that launchd cannot open a shell script living on `/Volumes/Data` (the secondary SSD) — `shell-init: getcwd: Operation not permitted` plus `/bin/bash: <path>: Operation not permitted`. **The schedule fires fine**; `com.fryanpan.doc-triage` has log entries from its 09:00 slot the day this was written. So they fire on time and then die at exec, which looks identical to never firing. See the secondary-volume entry above for the working shapes. This does not clear the exit-**78** quiet-hours job, which is a different code and still unexplained — don't merge the two again.
- **Most likely cause (of the exit-78 case only):** macOS **Background Task Management (BTM)** re-approval gate flipped by the OS update — `launchctl` cannot override it; the fix is a **GUI re-approval in System Settings → General → Login Items & Extensions** (user-only). Not CLI-confirmable without sudo (`sfltool dumpbtm`).
- **Bridge that works:** a session-cron in the always-up team-lead session runs the (working) script from session context (`CronCreate` mute 21:00 / unmute 08:00 → `/bin/zsh …/mac-mini-quiet-hours.sh {mute,unmute}`). Caveat: `CronCreate` auto-expires in 7 days + dies on TL respawn — a **stopgap, not durable**. Durable fix = the GUI re-approval, then retire the cron.

## Fleet-wide `--mode all` Respawn Kills Octoturtle's Discord (Handshake Race) — Solo Respawn Fixes It (2026-07-24)
- **Symptom:** after a `respawn.py --mode all --execute` (used here for the Team→Max pool switch), Octoturtle's Discord went dark — `mcp__plugin_discord_discord__*` tools absent from its registry, `fetch_messages` → "No such tool available." Same silent-handshake-failure class as 2026-07-13.

The fleet-wide respawn spawns ~15 sessions near-simultaneously, all racing to start plugin MCP servers; Octoturtle's discord channel lost the race and never registered. Process-table tell: **zero `bryanchan` `bun …discord/0.0.4 start` children running** before the fix; a live one (PID under Octoturtle) appeared only after the solo respawn.
- **Fix: clean SOLO respawn of just Octoturtle when the fleet is already settled** (no competing simultaneous spawns) — `tmux kill-session` → sweep orphan hive-mcp + orphan bryanchan discord bun → `tmux new-session … -e DISCORD_STATE_DIR=<real> … 'claude --continue'` → dismiss dialogs → verify FROM INSIDE (tools registered + live `fetch_messages` returns history + a test send returns a real message id). All three went green on the retry.

But Octoturtle connected + read + sent successfully *while that account's bot stayed live* — impossible if they shared a token (Discord allows one gateway per token). ∴ different bots, no conflict. Don't chase that account's processes; they're a red herring. (Also: reading another user's `~/.claude/discord` state is correctly blocked by the auto-mode classifier — don't try to inspect another account's secrets to diagnose; the empirical connect-test settles it without that.)
- **Prevention:** after ANY `--mode all` fleet respawn, treat the Discord-bearing session (Octoturtle) as needing an explicit post-respawn in-session verification (tools + live read), and solo-re-respawn it if dark. `SPAWN_STAGGER_SEC` isn't enough to protect the discord channel specifically. Candidate hardening: have respawn.py spawn the discord session LAST + alone, or auto-verify it and solo-retry.

## Discord Bot = One Session, One Token — A Second Claimant Silently Breaks It (2026-07-18)
- **A Claude Code "Discord bot" is just a session running with `--channels plugin:discord@...` — the session itself holds the Discord gateway connection; there is NO separate daemon.** (Confirmed via docs + claude-code-guide.) So the bot only replies while that session is alive, and there is no built-in keepalive — you supervise the session yourself (tmux/respawn). This is standard/inherent, not a bug.
- **Discord allows exactly ONE gateway connection per bot token.** Octoturtle's setup had TWO claimants on the same token: the documented dedicated `discord-session` git-worktree bot AND the main always-up Octoturtle session (respawn.py's `discord_state_dir_for` hands the real discord dir to any peer with a local `access.json`, so the main session also connected). Two sessions fighting over one gateway → intermittent connect/disconnect = the "flaky Discord" symptom, on top of the reboot outage (worktree was gone).
- **Fix: exactly one owner.** Bryan's call: the always-up main Octoturtle session IS the bot (no worktree). Removing the redundant worktree bot + a clean respawn of the main session (so it re-handshakes as sole claimant) fixed it — verified read-path (live `fetch_messages` history) AND send-path (replies posted with real Discord message IDs), zero conflict errors. respawn.py already gives it the real discord dir, so no spawn-config change was needed.
- **Same silent-failure class as the MCP-handshake bug: you cannot tell "connected" from "loaded" or from the process table.** A respawned session shows the channel "loaded" in the pane regardless of whether the gateway actually connected. Ground truth only comes from inside the session (does a live channel read return history? does a reply post return a message ID?). Believe the peer's in-session test, not the pane. The still-open prevention item is a startup health-check that asserts *connected*, not just *loaded*.

## Fleet Ran Off A Stale Branch For 6 Weeks — Directory-Source Installs Decouple "What Runs" From main (2026-07-18)
- **The fleet plugin installs from a local `directory` source, so peers run whatever was in the local working tree at install time — NOT origin/main.** Consequence: main going stale had zero operational effect. The fleet ran fine off a Jul-11 local snapshot while main sat 6 weeks behind (last real update Jun 4). Nobody noticed until a peer tried to distribute new work and found the fleet running from a frozen cache, not main.
- **Three compounding causes:** (1) work continued on a branch that had already been merged (PR #3) instead of branching fresh from main → it became a long-lived personal branch with 6 unpushed commits; (2) open PRs piled up because branch protection needs a review and the fleet correctly won't self-approve — with no reviewer, PRs aged out (one open 8 weeks); (3) no check ever asserted "the fleet must run from main," so the drift was invisible.
- **Recurrence guard: reinstall the plugin from main after every merge; never run the fleet off local branch state.** Fleet changes go PR → main → reinstall-from-main → reload. The `self-update` skill's `git pull --ff-only origin main` is the enforced path. Add a drift check (does the installed cache match origin/main?) to the token-watch or a weekly audit. Keep branches short-lived.
- **Public-repo hygiene surfaced during the fix (ai-team-lead is PUBLIC):** the naive "merge everything to main" would have pushed managed-project names — in the token-control trend log, an internal planning-docs folder, and a fleet security rule naming a peer. Fix pattern: gitignore private ops/planning docs (like retrospective.md), genericize peer/collaborator names out of shipped rules, and — because the leaky branch history was all local/unpushed — build a FRESH branch off origin/main containing only the scrubbed final tree (squash) so name-bearing intermediate commits never reach GitHub. Verify residual scrub flags are ONLY intentional already-public names before any SCRUB_SKIP push.

## Killing A Peer's Process: Confirm The Target With Its Owner First (2026-07-16)
- **During an overnight-builder cleanup I hard-killed the WRONG process — the Fable builder itself, not the "runaway" I meant to stop — because I mis-identified the PID and didn't confirm the target with the session that owned the runaway.** Recovery was clean only because Claude respawns with `--continue` (context intact); the kill was both mistargeted AND unnecessary (the real runaway was already gone).
- **`ps -axww -p <PID>` silently ignores `-p`.** The `-a` selects ALL processes, so `ps -axww -o args= -p 63284 | grep -oE '--model ...'` scanned every process and returned a stray `--model opus` — not 63284's real flag (`--model fable`, the builder). I concluded "63284 is the Opus runaway" and killed it; it was the builder. To inspect ONE pid use `ps -ww -o args= -p <PID>` or `ps -o args= -p <PID>` (NO `-a`). Killing by explicit `kill <PID>` is fine — it's the *identification* step that was corrupted.
- **Confirm with the owner before killing a process another session spawned.** The actual runaway was an IN-PROCESS teammate of the ADFA-4128 session (no OS PID of its own), which it had already `TaskStop`'d minutes earlier; the worktree was verified static (md5 over 8k files, zero diffs). Nothing needed killing. One question to the owning session ("which PID is the runaway / is it still alive?") would have shown the target didn't exist as a separate process and that 63284 was the builder.
- **A second session in the same git worktree does NOT appear in `list_peers`** — same path → same `stable_id`, so it collides with/masks the first. Detect co-writers via `ps` + cwd (`lsof -a -p <pid> -d cwd`), not `list_peers`. (A worktree is a single-writer resource.)
- **`list_peers` summaries LAG reality.** The A56 device owner's summary still read "driving Maps QA on the A56" for 20+ min after it had handed the device off by direct message — and I told the builder "device not free" on the strength of that stale summary. A peer's direct message is current; its `set_summary` is stale by construction. Don't gate decisions on a summary when a direct message contradicts it.

## Project Path Rename
- When a managed project directory is renamed (`mv old new`), `claude --continue` from the new path will NOT find prior history. Transcripts are stored under `~/.claude/projects/<encoded-realpath>/` where encoding replaces `/`, `_`, `.` with `-`. Fix: rename the transcript dir to match the new path's encoding before respawning. Also update `registry.yaml`'s `path` field. The peer's `stable_id` (derived from cwd) will change — past `to_stable_id` references in other agents' memories break.

## Plan Mode
- Skip plan mode for simple deliverables (writing a doc, creating a ticket, small edits). Plan mode adds ~6 min overhead and is only worth it for multi-file implementation work.

## Skill Editing
- When inserting a step into a numbered skill list, renumber all subsequent steps in a single edit rather than one-at-a-time — cascading individual edits are error-prone and slow.

## Notion MCP
- **`command: "replace_content"` on `notion-update-page` overwrites the ENTIRE page body with `new_str` — it is NOT a scoped find/replace.** `selection_with_ellipsis` is silently ignored; passing one cell's worth of text wipes everything else (verified 2026-06-03: a one-cell edit flattened a whole weekly-plan table to a single line). To change one cell/paragraph, fetch the full page first and pass the COMPLETE intended body as `new_str`. Recovery: if you still have the pre-edit fetch in context, re-`replace_content` with the full reconstructed body; otherwise tell the user to use Notion's page history (⋯ → Page history). Reconstructing a table from markdown loses colgroup column widths (cosmetic).
- `allow_deleting_content: true` on `replace_content` will archive child pages embedded in the old content. Destructive and hard to undo. Use `replace_content_range` or `insert_content_after` instead.
- When replacing content on a page with child pages, always preserve `<page url="...">` tags in the new content to avoid archiving them.

## Brainstorming
- When the user has already described the problem space clearly (e.g., a detailed `/new-project` request), fast-track to a first-cut design after 1–2 targeted questions. Don't run a full clarifying sequence — the user feels like they're repeating themselves if you ask about things they already covered.

## GitHub API
- For brand-new repos with no commits: clone locally, make an initial commit, then push to create `main`.
- Fine-grained PATs do NOT have a "Checks" permission. The check-runs API (`/repos/.../commits/.../check-runs`) is inaccessible. Use the commit-statuses API (`/repos/.../commits/.../status`) instead, which needs the "Commit statuses: Read" permission.

## CI Workflow & Multi-PR Coordination
- CI triggers on `pull_request` events only (not `push`). Pushes to feature branches don't trigger CI — only opening or synchronizing a PR against `main` does.
- When merging multiple PRs that touch the same repo, rebase sequentially — merging one changes the base and creates conflicts in the others.

## Bun Test Mock Isolation
- `mock.module()` in `bun:test` is **process-global** and persists across all test files in the same run. Never use `mock.module()` for modules that other test files also test.
- `globalThis.fetch` replacement leaks across test files unless explicitly restored. Use `spyOn(globalThis, "fetch")` with `mockRestore()` in `afterEach` instead.

## Python Environment
- When `python3` commands fail with permission errors or missing packages, check whether a version manager (uv, pyenv) is installed before retrying. `which uv && uv python list` or `which pyenv && pyenv versions` diagnoses the issue faster than repeated shell attempts.

## Git Hard Links
- Git does not preserve hard links across checkouts. If two files share an inode (e.g., a script hard-linked into two skill directories), `git checkout` replaces them with independent copies. Track both and accept divergence — or use a symlink if one canonical location is acceptable.

## Agent Cost Patterns
- Reducing turns matters more than reducing prompt size — cache reads dominate token cost.
- **Implementation-subagent pattern:** dispatching a multi-turn implementation phase as a subagent via the `Agent` tool gives it fresh context instead of the parent's growing history. The bigger the implementation, the bigger the savings.
- **Haiku for low-intelligence polling loops:** CI waits, event watches, retry loops — use Haiku, not Sonnet.
- Subagents dispatched via the `Agent` tool don't get custom MCP tools *auto-loaded* in their base toolset — but they CAN load them on demand via `ToolSearch` (deferred-tool mechanism). Verified 2026-07-11: a Sonnet subagent successfully loaded `mcp__claude-in-chrome__*` and could see `claude-hive`, `live-feedback`, etc. So browser/UI QA CAN be delegated to a subagent (see the `qa-delegate` skill). The old "just use Bash" workaround for CI status still works but is no longer forced.
- Keep total `alwaysApply: true` rule content in a repo under ~80 lines — it multiplies across every turn.
- **`alwaysApply` rules leak into subagents.** A subagent dispatched via the `Agent` tool inherits the parent's rules, so a rule written for top-level peer sessions gets followed by subagents too. `claude-hive-peer.md` told peers to send 3–5 status updates per task; QA subagents obeyed it, loaded claude-hive via ToolSearch, and pinged progress back — every ping landing in the *parent's* context, which is the exact cost delegation exists to avoid (found 2026-07-12). Any rule that prescribes outbound messaging needs an explicit "subagents: not you" gate at the top.

## Plugin MCP Handshakes Fail Silently (2026-07-13)
- **Never respawn the fleet all at once.** Simultaneous spawns make every session race to start its plugin MCP servers; some handshakes lose and Claude gives up on those servers. `respawn.py` now staggers spawns (`SPAWN_STAGGER_SEC`).
- **A failed MCP handshake is completely invisible from outside the session.** The child process still spawns and still sits there — it just never gets spoken to. There is no error, no warning, and no log. Worse, every external signal is identical to a healthy server: CPU time (a connected Discord gateway heartbeats at ~0.01s, same as a process doing nothing) and open sockets (the *healthy* Discord child held zero ESTABLISHED sockets). Both heuristics were tried and both false-positived the known-good peer.
- **So "the process is running" proves nothing, and neither does anything else you can see from the process table.** The only reliable check is from *inside* the session: ask the peer whether its tools actually surfaced.
- Cost: Octoturtle silently lost its Discord channel for 3 days — process up, config valid, token valid, no errors, agent simply unreachable on its primary user-facing surface. It was only caught because Bryan noticed he wasn't getting replies.
- Corollary for debugging: I twice concluded "X is broken/fine" from process-table forensics and was wrong both times. When a peer reports a capability is missing, **believe the peer over the process table** — it can see its own tool registry and you cannot.

## A Fleet Peer Can Be Working In Someone Else's Repo (2026-07-14)
- **A hive peer is indistinguishable from a normal fleet member even when its cwd is a public/other-owned repo.** The hive connection comes from launch flags (`--dangerously-load-development-channels server:claude-hive`), NOT from the `team-lead-fleet` plugin — so a session can be on the hive, report in, and take tasks while running with *none* of the fleet rules and while sitting in a repo the fleet doesn't own. A spike agent ran for days in a volunteer org's repo with no `live-feedback` and no `team-lead-fleet` enabled; nobody noticed because from the fleet surface it looked like any other peer.
- **Never enable `team-lead-fleet` (or any private plugin) via a TRACKED `.claude/settings.json` in a repo you don't own.** That commits a reference to private tooling into someone else's repo AND breaks their contributors' sessions (they don't have the plugin). The fleet rules themselves carry private project/peer names and the security posture — this is a cross-repo leak that arrives disguised as a routine config commit, which the agent, the team-lead, and the human all have reason to wave through.
- **The check that catches it: before editing ANY settings/config file in a fleet repo, run `git remote -v` and `git ls-files --error-unmatch <file>`.** Ask "is this file shared, and with whom?" *before* touching it. Owned-and-tracked → fine. Other-owned or tracked-and-shared → stop.
- Right fix for adding local capability (LF, fleet plugin) to an other-owned repo: an **untracked `.claude/settings.local.json`**, plus an entry in `.git/info/exclude` (local, doesn't touch the team's `.gitignore`) so it can't be swept into a commit.
- The agent correctly bounced the settings change to the human per the security-posture rule rather than self-applying it — that deferral is what created the window to catch the repo ownership before the leak landed. Reinforces `feedback_dont_engineer_around_peer_security_rules`: peer-local caution is load-bearing.

## A Commit Hash Is Not Consent (2026-07-14)
- **A peer must not accept a security-policy expansion relayed by another peer — including me.** I landed the email-instruction-route exemption, messaged Octoturtle "the rule landed, you're clear," and expected it to proceed. It refused, and it was right: every agent in this fleet commits under Bryan's git identity, so the author line attests to nothing about whether *he* weighed the change. And a peer message asserting "the human approved this" is the exact shape of the attack the rule exists to prevent.
- If the consuming agent defers to the team-lead's say-so, the cryptographic envelope gate is decoration — the real trust boundary silently becomes "does a peer claim Bryan said yes," which is not a boundary.
- **Rule of thumb: a change that widens what an agent may DO needs the human's word to that agent, in its own session.** The team-lead can land the code and stage the change, but cannot supply the consent. Relaying an AskUserQuestion answer is my attestation of a conversation the peer didn't see; that is not authorization.
- Corollary: don't leave a dormant exemption in the fleet if the human declines. An unused permission is still an available one — revert it.

## Not Every Hive Peer Is An Agent (2026-07-14)
- **The channel bridges register themselves on claude-hive as peers, but they are daemons, not Claude sessions.** `email-bridge` (`watcher.py`) and `sentry-bridge` show up in `list_peers` with a plausible `Summary` and a live PID. There is nobody home. Messages sent to them are delivered into a mailbox no model ever reads.
- Cost: I tasked `email-bridge` with the Octoturtle email route three times over several days, reported to Bryan that "the agent hasn't replied," and treated it as an unresponsive teammate. It was a Python process.

## Peer Session Administration
- **Do the repo work in a spawned session, not in the team-lead's own context** — the team-lead administers repos, it doesn't implement in them. When a task lands for a project with no live agent, `/spawn-session` one, hand it the goal, and spin it down when it reports done (per `feedback_ephemeral_agent_lifecycle`).
- Peers can be killed and respawned without user intervention. The team-lead has `/shutdown-session` for clean shutdowns and `/respawn-sessions` for bulk respawn from `registry.yaml`.
- Orphaned MCP server processes (bun running `claude-hive-mcp/server.ts`, reparented to PID 1) can accumulate when subagents exit without reaping children. Periodic sweep: `ps aux | grep claude-hive-mcp/server.ts | grep -v grep | awk '{print $2}' | xargs kill`.

## Plugin Subagents
- Plugins ship subagents from an **auto-discovered `agents/*.md` dir** — no `plugin.json` declaration. The `subagent_type` is **namespaced**: `team-lead-fleet:writing-editor`, not `writing-editor`. Plugin agents ignore `hooks`/`mcpServers`/`permissionMode` frontmatter (security).
- The `skills:` frontmatter field **preloads** skill content into the subagent at startup. This is how you make a skill unforgettable: bind it to the agent rather than trusting the agent to load it. Verified — the subagent never calls `Skill` and still applies the content.
- **The default subagent contract forbids what a writing subagent exists to do.** Every subagent gets "Do NOT Write report/summary/findings/analysis .md files. Return findings directly as your final assistant message," and general-purpose adds "NEVER proactively create documentation files (*.md)." A subagent whose deliverable *is* a file must override this explicitly or it fights its own base prompt.
- **Test plugin changes with `claude -p --plugin-dir <path>`** — loads a plugin for one session only, so you can RED/GREEN a fleet-wide change without repointing the live fleet's installed copy. `--output-format stream-json --verbose` shows the actual tool calls, which is the only way to know whether a trigger fired vs. the model doing the right thing by another route.

## Rules vs Skills (triggering)
- **A rule telling agents to delegate loses to a skill whose description matches the task.** Measured: with both present, the session called `Skill(writing-for-readers)` and wrote the doc itself instead of dispatching the subagent. superpowers' `using-superpowers` mandates skill invocation forcefully; a mild paragraph inside ~500 lines of injected rules doesn't compete. Fixes that worked: name the loophole in the rule ("don't load a writing skill to help you write it better") **and** retarget the skill's `description` so a top-level session doesn't match it. 0/4 → 4/4.
- Corollary: **a skill that a subagent preloads doesn't need a discoverable description.** Writing one invites the parent to grab it — which spends exactly the context delegation was meant to save.
- The `alwaysApply:` frontmatter on `plugin/team-lead-fleet/rules/*.md` is **vestigial**. `hooks/session-start.sh` concatenates *every* file in `rules/` into SessionStart context regardless of it. Injected total is ~660 lines — ~8x the ~80-line budget above.

## Evaluating Whether Guidance Is Needed
- **Run the no-guidance control before writing the guidance.** Nine agents given raw spike notes and no writing guidance produced reader-first docs with light structure 9/9 — the assumed "over-formalism" failure (ADR blocks, option matrices) never appeared.
- **CORRECTED 2026-08-03 — the harness writing block is model-specific, and this entry's original claim is false on Opus 5.** It used to assert that the Claude Code system prompt "already ships `Lead with the outcome` / `write for a teammate who stepped away` / `tables only for short enumerable facts` to every agent," and concluded "you'll mostly be restating the harness." Measured by direct probe: **fable-5 and sonnet-5 carry that block; opus-5 does not** — not in a main-loop session and not in a subagent. On opus-5 there is no prose guidance at all: no length rule, no jargon rule, no table rule. The nearest thing is about code ("write code that reads like the surrounding code"). So on opus-5, `communication.md` is not redundant — it is the only writing guidance the agent has.
- **That false claim then fed back through an agent and nearly deleted working guidance.** A reviewer auditing `communication.md` declared its inverted-pyramid section redundant "because the harness already says Lead with the outcome," citing its own context. Its context contained the phrase only because *this file* is injected via CLAUDE.md and quotes it. The learnings file asserted a fact about the harness, an agent read the assertion as evidence it held the harness instruction, and recommended cutting the real guidance as duplicate. **A confident claim in an injected doc is indistinguishable, to a reader, from the thing it describes.** Date claims about the harness, name the model measured, and re-measure at each release.
- **Watch for contaminated fixtures.** My first test named the reader in the prompt (pre-satisfying the rule under test); my second leaked it via the fixture's last line, and all 3 agents cited that line by name. Both looked like passes. Strip the cue and re-run.
- **Agents mimic their source's hedges rather than reasoning about evidence.** Measured: 9/9 correctly hedged the two claims the notes flagged as uncertain, while 6/9 invented *new* unhedged facts ("the branch is green", "most rides aren't 40km") — some load-bearing in an argument. Careful-looking output is not epistemic discipline; it's pattern-matching on the source's caveats and stopping where they stop. Related: 9/9 did zero re-derivation — excellent transcriptions, zero analyses.
- A skeptical **independent judge subagent**, told explicitly that a false "this is fine" costs more than a false "this is flawed", caught all of the above. Eyeballing the docs did not — they read as excellent.

## Tooling
- The `Write` and `Edit` tools require a file to have been read "recently" in the same session. If many tool calls have elapsed since the initial read, re-read the file immediately before writing/editing to avoid "file not read yet" errors.

## Working with Users
- Short, direct corrections ("don't bury the lede", "stop mentioning X") are the most productive feedback. Don't over-explain in response — just fix it.
- When the user says "set up X for the team," they often mean adoption guidance (how to install, how to use), not config files to commit. Ask which they mean if ambiguous.
- Before building a tool or script, ask about language preference and testing expectations. Don't assume bash is fine — they may strongly prefer Python (for testability) or another language. A 30-second question saves a full rewrite.

## When to Ask vs When to Act
- **Default to action, not questions.** When the user delegates, they expect work to start, not a questionnaire. The bar for asking is high.
- Only ask if BOTH: (1) genuinely ambiguous about WHAT to do (not HOW), and (2) cannot be determined by reading the code, comments, or linked docs.
- When writing delegation prompts or skill instructions, be specific and concrete. "Prefer X unless Y" is too vague — use explicit decision criteria and concrete examples.
